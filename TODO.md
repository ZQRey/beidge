### Задача Б: Исправления и улучшения качества бейджа и интерфейса

1. **Удаление надписи «линия сгиба» на PDF-макете:**
   - На сложенном бейдже вверху по центру выводится текст «ЛИНИЯ СГИБА», попадающий на видимую часть бейджа.
   - **Решение:** Удалить текстовый маркер `ЛИНИЯ СГИБА`, оставив лишь тонкую технологическую пунктирную линию для раскроя.

2. **Устранение перекрытия заголовка «КОДЫ ПО БЕЗОПАСНОСТИ» таблицей:**
   - На задней стороне блок «Белый» (первая строка сверху) физически перекрывает заголовок «КОДЫ ПО БЕЗОПАСНОСТИ».
   - **Причина:** Высота 5 строк (`row_h = 9.8mm`, `pad_y = 1.2mm`, `base_y = 2.5mm`) достигает координаты `y = 56.3mm`, в то время как заголовок отрисован на `y = 55.5mm`.
   - **Решение:** Скорректировать геометрию: `row_h = 8.8mm`, `pad_y = 0.9mm`, `base_y = 2.0mm`. Верхняя граница блока «Белый» опустится до `49.6mm`, обеспечивая свободный отступ до заголовка (55.0mm) более чем в 5 мм.

3. **Переименование заголовка вкладки/страницы в браузере:**
   - Сейчас в заголовке вкладки браузера отображается имя проекта по умолчанию — `frontend`.
   - **Решение:** В `frontend/index.html` и через хук `document.title` установить понятное название:
     - RU: **«Генератор бейджей»**
     - KK: **«Бейджтер генераторы»**

4. **Книжная ориентация PDF при отправке на печать:**
   - Сейчас файл генерируется в альбомном формате (`180 × 60 мм`, соотношение 3:1). При печати офисный принтер с лотком А4 распознаёт документ как «Альбомный» (Landscape), что разворачивает изображение и искажает стандартную подачу бумаги.
   - **Решение:** Сформировать страницу для печати в **книжной ориентации** (Portrait):
     - Стандартный лист А4 книжной ориентации (`210 × 297 мм`) с аккуратно отцентрированным бейджем и метками для обрезки/сгиба.
     - Добавить в метаданные PDF явный флаг книжной ориентации страницы.

5. **Дедупликация сотрудников в реестре:**
   - При каждой генерации PDF создаётся новый экземпляр `Employee`, даже если сотрудник с такими ФИО, должностью и отделением уже существует.
   - **Решение:** В методе создания бейджа (`backend/app/api/badges.py`) выполнять поиск существующего сотрудника по нормализованным `full_name` и `position` (без учёта регистра и лишних пробелов). Если сотрудник найден — использовать его `id` и обновлять отделение при необходимости, не создавая дубликат.

6. **Устранение предупреждения Super-Admin в GLPI (`session.cookie_secure = on`):**
   - В веб-интерфейсе GLPI под учётной записью администратора отображается предупреждение:  
     *«Директива PHP "session.cookie_secure" должна быть установлена в значение "on", если доступ к GLPI осуществляется по протоколу HTTPS.»*
   - **Решение:** В конфигурации Apache бэкенда GLPI (`/opt/glpi/sso-backend.conf`, смонтированной в контейнер `glpi-app`) добавить директиву `php_admin_flag session.cookie_secure On` и перезагрузить Apache. Интеграции и автовход продолжат работать штатно.

### Задача В: Сеть, HTTPS (порт 443), сертификат AD CS и привязка к `beidge.gp1.loc` (172.16.16.11)

> [!IMPORTANT]
> **Новые сетевые параметры сервиса:**
> - IP-адрес: **`172.16.16.11`** (маска `/23`, шлюз `172.16.16.2`, DNS `172.16.16.31`)
> - Доменное имя: **`beidge.gp1.loc`** (запись типа A уже настроена в DNS на `dc01.gp1.loc`)
> - Порт: **443 (HTTPS)** с автоматическим редиректом с 80 (HTTP)
> - Центр сертификации: **`dc01.gp1.loc\gp1-DC01-CA`** (AD CS, шаблон `WebServer`)

**План внедрения HTTPS:**
1. **Закрепление сетевой конфигурации `172.16.16.11/23` на хосте:**
   - Сделать привязку статического IP постоянной в `/etc/network/interfaces`.
2. **Выпуск доменного сертификата через AD CS (`dc01.gp1.loc`):**
   - Сгенерировать закрытый ключ RSA 2048/4096 бит и CSR с SAN:
     - `DNS: beidge.gp1.loc`
     - `DNS: beidge`
     - `IP: 172.16.16.11`
     - `IP: 172.16.17.177` (для переходного периода)
   - Подписать запрос на CA `dc01.gp1.loc\gp1-DC01-CA` по шаблону `WebServer` (используя права доменного администратора).
   - Собрать цепочку `fullchain.pem` (сертификат + корневой CA `gp1-DC01-CA`).
   - Сертификат будет автоматически доверенным на всех рабочих станциях домена GP1.LOC без предупреждений безопасности браузера!
3. **Настройка Nginx на 443 порт:**
   - В `docker-compose.yml` опубликовать порт `443:443` и пробросить том с сертификатами.
   - В `nginx/nginx.conf`:
     - Настроить блок `server { listen 443 ssl http2; server_name beidge.gp1.loc 172.16.16.11 localhost; ... }`.
     - Настроить SSL-параметры (TLS 1.2, TLS 1.3, надежные шифры).
     - Добавить редирект с `listen 80;` на `https://$host$request_uri;`.
4. **Настройка GLPI API для подсети `172.16.16.0/23`:**
   - В `glpi_apiclients` разрешить диапазон `172.16.0.0` - `172.16.255.255`.

### Задача Г: Пакетная генерация и групповой заказ бейджей (1–5+ сотрудников) на листе А4

Предоставить старшим отделений, заведующим и кадровой службе возможность генерации и заказа бейджей сразу на группу сотрудников (2, 3, 4, 5+ человек):
1. **Интерфейс конструктора на главной странице:**

   - По умолчанию выбран 1 сотрудник (привычный быстрый режим).
   - При выборе > 1: динамический список карточек для каждого сотрудника (ФИО, Должность, Отделение).
   - Опция общего отделения («Отделение по умолчанию для всех» с автозаполнением), чтобы старшей отделения не приходилось вводить название отделения повторно для каждого человека.
   - Поддержка виртуальной клавиатуры казахских букв (`Ә`, `І`, `Ң`, `Ғ`...) для любого активного поля ввода.
   - Интерактивный предпросмотр: переключение между сотрудниками для проверки каждого бейджа перед печатью/отправкой.
2. **Оптимальное размещение на листе бумаги А4:**
   - При генерации PDF все выбранные бейджи компонуются на книжном листе А4 (`pagesize=A4`).
   - На одном листе А4 книжной ориентации вертикально размещается до 4 сложенных бейджей (180 × 60 мм каждый, с линиями сгиба и метками реза).
   - Если выбрано от 1 до 4 человек — они умещаются на **1 листе А4**.
   - Если выбрано 5 (или более) человек — автоматически формируется многостраничный документ (по 4 бейджа на страницу).
3. **Групповая заявка в GLPI («Передать программистам»):**
   - Вместо создания 3-5 отдельных заявок формируется **одна сводная заявка**:
     - Тема: `[{machine_name}] Заказ бейджей ({count} чел.): {department_name}`.
     - Текст заявки: детальный нумерованный список всех сотрудников с должностями и отделениями, а также данные заявителя (компьютер, кабинет, пользователь).
     - Вложение: один единый файл PDF с готовыми для печати бейджами на листе А4.
   - Максимальная экономия бумаги, времени старшей отделения и сотрудников IT-отдела.

### Этап 6: Сквозная авторизация (SSO), панель локального администратора (LDAP/GLPI) и исправление отправки заявок

- [x] **6.1. Анализ причин и архитектурное решение**
  - **Причина «Доменный пользователь (ПК: Не определено)»:** Определение пользователя производилось исключительно по клиентскому IP через стороннюю таблицу Helper. На клиентском ПК агент помощника зафиксировал виртуальный IP (`169.254.213.92`) вместо LAN IP (`172.16.16.206`), в результате чего запрос вернул 404. При этом DNS-сервер (`dc01.gp1.loc`) по PTR-записи моментально разрешает `172.16.16.206` в `N2415600816.gp1.loc`.
  - **Причина «Пользователь: Telegram, Компьютер: Через GLPI»:** Из-за сбоя определения пользователя заявка создана с fallback-пользователем `Telegram`. Импортёр заявок Helper (`GlpiTicketImport.cs`) для заявок без префикса имени компьютера в теме подставляет дефолтное значение `"Через GLPI"`.
  - **Решение:** 
    1. Реализовать сквозную авторизацию пользователей AD через Kerberos/SPNEGO и LDAP с автоматическим извлечением ФИО, логина и имени рабочей станции (PTR DNS / AD).
    2. Добавить панель локального администратора с отдельным паролем для гибкого управления параметрами LDAP, GLPI и тумблером включения/отключения SSO.
    3. Исправить шаблон заявки: убрать дублирующий блок «--- Информация о заявке ---» и передавать имя ПК в теме заявки для корректного отображения в Telegram-боте.

- [x] **6.2. База данных: модель настроек и локальный администратор**
  - В `backend/app/models/` созданы модели `SystemSetting` и `AdminUser` (хранение в PostgreSQL):
